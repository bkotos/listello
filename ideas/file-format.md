# Listello Markdown File Format Notes

## Core Philosophy

Listello `.listello.md` files should balance:

- Human readability
- Machine readability
- Git friendliness
- Markdown renderer compatibility
- Long-term extensibility
- Flexible editing

The design philosophy is:

```text
Structured data -> authoritative machine-owned fields
Markdown body -> human-authored content
```

## High-Level Structure

A `.listello.md` file consists of:

1. YAML frontmatter
2. Human markdown body
3. Optional Listello-owned structured blocks

Example:

```md
---
id: todo_01K2XA
title: Replace pool liner
status: next
priority: high
createdAt: 2026-05-07T20:00:00Z
updatedAt: 2026-05-07T20:30:00Z
---

# Replace pool liner

Need to measure dimensions and compare replacement options.

## Notes

Pool liner has tearing near the seam.
```

## Authoritative Data Rules

The YAML frontmatter is authoritative for structured data.

Examples:

```yaml
status:
priority:
dueAt:
assignedTo:
tags:
createdAt:
updatedAt:
```

The markdown body is not authoritative for structured state.

Do not parse this from prose:

```md
Status: next
Priority: high
Due tomorrow
```

Instead, store it in frontmatter:

```yaml
status: next
priority: high
dueAt: 2026-05-10T00:00:00Z
```

## Markdown Body Philosophy

The markdown body should be treated as largely opaque by the core engine.

Meaning:

- users can structure content however they want
- headings are convenience only
- parser should not depend heavily on markdown structure
- markdown is primarily for humans

Good:

```md
# Notes

Need to compare installer pricing.
```

Also good:

```md
Need to compare installer pricing.
```

The parser should not care much about either.

## Comments Design

Comments should:

- live inside markdown
- render nicely in GitHub, Obsidian, etc.
- still be machine-readable
- preserve authoritative metadata separately

The recommended approach is:

- HTML comment metadata blocks
- optional rendered display block
- markdown body content

## Recommended Comment Format

```md
<!-- listello:comment
id: cmt_01K2XA
author: brian
createdAt: 2026-05-07T20:30:00Z
updatedAt:
-->

<!-- listello:rendered -->
> **Brian** · May 7, 2026 at 4:30 PM
<!-- /listello:rendered -->

Measured the pool: 10 ft x 20 ft.

Need to verify whether the liner is overlap or beaded.

<!-- /listello:comment -->
```

## Parsing Rules

Inside `listello:comment`:

```text
- parse YAML metadata from opening block
- ignore anything inside listello:rendered
- remaining markdown is authoritative comment body
```

Meaning:

- metadata is authoritative
- rendered header is disposable/generated
- comment body is user-authored markdown

## Important Principle

The visible rendered line:

```md
> **Brian** · May 7, 2026 at 4:30 PM
```

is not authoritative.

The authoritative source is:

```yaml
author: brian
createdAt: 2026-05-07T20:30:00Z
```

Listello may regenerate the rendered block at any time.

## Ownership Model

### Listello-Owned Content

These are controlled or generated by the application:

```text
YAML frontmatter
listello:comment metadata
listello:rendered blocks
future structured blocks
```

These may be regenerated.

### User-Owned Content

These are authored by humans:

```text
markdown descriptions
notes
comment body markdown
brainstorming
research
references
```

Listello should preserve these faithfully.

## Suggested Future Structured Blocks

Potential future extensions:

```md
<!-- listello:attachment -->
<!-- listello:activity -->
<!-- listello:checklist -->
<!-- listello:ai -->
```

## Design Philosophy Summary

```text
Metadata is authoritative.
Markdown is flexible.
Rendered markdown is graceful fallback UI.
Listello UI is the rich canonical UI.
```

## Recommended Mental Model

```text
Frontmatter = database columns
Markdown body = document
Listello blocks = structured embedded objects
```

## Recommended File Extension

```text
.listello.md
```

Examples:

```text
replace-pool-liner.listello.md
todo_01K2XA.listello.md
```

## Recommended ID Strategy

Prefer ULIDs over UUIDs.

Example:

```text
01K2X9X6A3M8YQ7F4C2N8P1ZB
```

Benefits:

- sortable
- filesystem friendly
- human friendlier
- deterministic ordering
